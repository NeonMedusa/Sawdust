# 音频文件 / 采样器 — 设计（v1 定稿）

> 本文是 2026 年讨论定稿的设计基线。实现按 **P1 → P2 → P3** 推进；
> 未列进"v1 范围"的一律**不做**（见 §9 非目标），不要"顺手加"。

## 1. 目标

1. **音频文件进入工程**：WAV / FLAC / MP3 / OGG-Vorbis 可由用户加载、引用、播放；
2. **采样器鼓组层**：鼓垫的层可以是"真实采样"（一次性、原速）——层 = 乐器槽的
   既有架构直接支持（`docs/drumkit.md` §7 预留）；
3. **播放列表音频片段**：音频像样式片段一样可拖放/裁剪，波形入片段；
4. **单文件追求不变**：所有编解码编进 `Sawdust.exe`，不引入 DLL。

## 2. 编解码（调研定稿：零新依赖）

已 vendored 的 **miniaudio v0.11.25** 内置解码器（宏实测）：
`MA_HAS_WAV` / `MA_HAS_FLAC` / `MA_HAS_MP3` / `MA_HAS_VORBIS` ✓ —— 且
`miniaudio_impl.c` 无任何禁用宏 → **早已编进每个构建**（ReleaseFast ≈ 3.19MB 已含）。

| 格式 | 来源 | 许可 | 结论 |
|---|---|---|---|
| WAV / FLAC / MP3 / OGG-Vorbis | miniaudio 内置 | PD / MIT-0 | ✅ v1 |
| Opus | libopus+opusfile（BSD-3；源码编进 exe 或自定义后端） | BSD-3 | 以后 |
| AAC | faad2=GPL / FDK-AAC=专有条款 | ✗ | **放弃**（提示用户转码） |
| AIFF/CAF | miniaudio 无 | — | 跳过（以后可自写 PCM 解析） |

API 要点（`audio.zig` 已 `@cImport` miniaudio.h）：
- **`ma_decoder_init_file_w`（宽字符路径）必用**——中文路径老坑（见 `pitfalls.md`）；
- `ma_decoder_config_init(f32, 2, 0)` → **不重采样**（原生率直出）；播放侧靠 `SampleData.ratio`（原生/引擎）换算采样帧——导入更快，且改引擎采样率不再需要重解码；
- `ma_decoder_get_length_in_pcm_frames`（时长/波形）；`ma_data_converter_*` 留给流式（以后）。

文件拖入：窗口层补 `DragAcceptFiles` + `WM_DROPFILES`（尚未支持）；另有"浏览文件…"入口。

## 3. 资产层（AudioAsset）

```
AudioAsset = { 绝对路径（内存态）, 解码缓冲 f32@**原生采样率**（+ ratio）, 峰值缓存（min/max 分桶；与解码单遍、桶大时抽样）,
               引用计数 }
```

- 按路径去重；鼓采样与音频片段**共用**同一资产；
- v1 **整文件解码进内存**（鼓采样毫秒级；长音频设上限 + 提示；流式播放以后）；
- 释放：引用计数归零 + 帧末回收（沿用退役链纪律）。

## 4. 音频样式（AudioStyle）——片段共享的"内容"

**与音符样式对称**（样式 = 内容、片段 = 摆放）：

```
AudioStyle = { 编号, 名称, 来源资产, 混音通道, 增益 }
```

- **推子/通道 = 样式级**（用户拍板 2026-10）：双击窗口里的通道/增益调整作用于
  该样式的**所有片段实例**（窗口内标注"此采样全部实例共用"）；
- **片段级增益 v1 不做**（以后"真的"有需求再加）；
- 拖入同一文件第二次 → **按路径复用已有音频样式**（同"点样式"直觉）；
- 混音台只多"一个音频源一个通道条目"，不因实例数膨胀。

## 5. 音频片段（AudioClip）

```
AudioClip = { 轨道, 时间轴起止（步）, 采样内起点/终点（帧 trim）, 引用 AudioStyle }
```

- 拖动/裁剪/层级/沉底与现有片段同手感（复用 `topmostClipAt`/沉底等机制，
  按片段种类分派）；**双击 = 打开音频窗口**（样式片段双击仍是钢琴卷帘）；
- 一段音频被裁成多段（不同 trim）时各成一片段、共享样式推子。

## 6. 播放模型（音频线程）

- **不走调度事件**：音频线程**每块"活动片段扫描"**——按当前传输位置判断哪些
  片段应在响：进入 → 起播（含采样内偏移）、离开 → 停、跳转/循环 → 按新位置
  重算偏移重启（天然支持跳转/撤销/循环，不动调度器）；
- v1 **原生速率、无时间拉伸**；片段长度与音频时长独立（截断播放）；
- 混入**样式的混音通道**（与乐器同一条通道链：EQ/效果/推子照常）；
- 每片段一行发布到音频线程（片段索引 → 通道/增益/采样指针/trim）——**只增不减**
  的容量纪律同池化层（`docs/resources.md`）。

## 7. 窗口（两个入口，同一实现）

一个"波形编辑器面板"，两种挂载：

| 入口 | 内容 |
|---|---|
| **音频片段窗口**（双击音频片段） | 波形（本片段 trim 段高亮）+ 起点/终点手柄 + 试听（游标/播放/暂停）+ **样式级**通道/增益 |
| **采样器层窗口**（鼓垫层行 [编辑]，`LayerKind.sampler`） | 波形成员 + 同款试听/trim + 根音（=垫音高）/一次性/层增益 |

- **试听 = 局部预览**：独立于主传输（不动主播放游标）；走各自通道
  （片段走样式通道、鼓层走鼓组乐器通道）——用户拍板 ✓；
- v1 **不做波形缩放**（先原型看手感，之后再议——钢琴窗同款 Ctrl+滚轮手势可复用）；
- 波形峰值：资产层加载时算好分桶 min/max，按像素宽取样绘制。

## 8. 采样器（鼓组层）

- `LayerKind += sampler`（一次性 one-shot，v1）；
- 层字段：来源资产、采样内起止、增益（已有 `gain`）；
- 播放：**原速一次性**（垫音高不改变速度；"跟随音高变调"是另一个设计，
  用户明确 v1 不做）；复用层 = 乐器槽的整套基建（事件按音高分发 ✓ 已现成）；
- 采样器层的试听由采样器窗口负责（同 §7 面板）。

## 9. 非目标（v1 明确不做）

变速/变调播放、时间拉伸、流式播放、波形缩放、片段级增益、AAC、Opus、
音频内嵌进工程、AIFF/CAF、采样循环/门限模式、多采样力度分层、round-robin。

**多声道（5.1 / 7.1）——无限期延后**（用户拍板）：商用 DAW 里很多都不做，
而唱片公司发布的音频绝大多数就是双声道；真要做也是一个独立立项（见 §8 末尾）。

## 10. 存档

## 8. 导入性能路线图（P1/P2/P3）

> 记录于实测"拖入音频整程序卡死"之后。P1 已落地；P2/P3 待排期。

### P1（已完成）：解码提速
- **不重采样**：`ma_decoder_config_init(f32, 2, 0)` 原生率直出；`SampleData.ratio`
  （原生/引擎）+ `engFrames()`；引擎侧取样本处乘 ratio（片段扫描/试听/采样器声部），
  UI 与 trim 仍为引擎帧域。改引擎采样率不再需要重解码。
- **峰值与解码单遍**：桶 > 32 帧时按 `bucket/16` 步长抽样（只影响显示精度）。
- 效果：省掉整遍 SRC 与整遍峰值遍历；**窗口仍会阻塞**（解码本身还在 UI 线程）。

### P2（**已实现**，2026-10）：异步导入（真正消除冻结）
**目标**：拖入即见片段（按文件头时长给出正确长度），加载完成后自动填充。
实现见 `src/audio_import.zig`（`Manager` / `Job`）+ `App.audioStyleAddAsync()` / `pollImports()`。

1. **阶段 A（UI 线程，毫秒级）**：`Manager.probeFile()` 只读文件头（格式+时长）；
   立即建样式（`asset = -1`、`frames_hint = 引擎帧数`）+ 占位片段，入队。
   ⚠️ **不在入队时分配缓冲**：队列里只有元数据（否则拖 5 个 30 分钟文件 = 3.5 GB）。
2. **阶段 A′（UI 线程）**：排队到它时才 `alloc(frames + peaks)` —— 内存仍只在 UI 线程分配，
   同时只有 1 份在飞（= 单 worker 的自然上界）。
3. **阶段 B（**单个**常驻 worker 线程）**：`ma_decoder_init_file_w` 打开 → **分块**解码
   （`chunk_frames = 65536` ≈ 0.68 s）→ 边解边算峰值（`updatePeaks`，与同步导入
   **同一份算法**）→ 每块更新 `done_frames` 原子量（进度）。每块开头检查 `cancel`。
   worker **只写自己那块内存**，不碰 App、不分配、不 free。
   worker 空闲时用 `std.Io.futexWaitUncancelable` 睡觉（**零轮询、零 CPU**）。
4. **阶段 C（UI 每帧 `pollImports`）**：`done` → 缓冲**过继**给资产池并设 `style.asset`；
   `failed` → toast（片段保留为“音频缺失”）；`cancelled` → 直接丢弃缓冲。
   调用点在 `main` 主循环里、`rebuildAudioTable` **之前** → 同一帧就能出声。
- **取消/退出**：删样式 → `remapAfterRemove`（引用它的 job 取消、更大索引前移）；
  撤销/重做与换工程 → `cancelAll + drain`；退出 → `import_mgr.deinit()`（**join** worker）。
- **新建/打开工程**：`App.clearAudioEverything()` —— 作废导入 → **暂停设备** → 清样式 +
  `resetAudioAssets()` → 在暂停窗口内**重发空播放表**（旧表退役）→ 恢复设备。
  顺序不能乱：先暂停再释放，否则音频线程可能还在读已 free 的资产。
- UI：波形区画斜纹 + “载入 N%”；窄片段只画斜纹。`frames_hint` 让占位片段的长度/宽度
  一开始就是对的（不靠默认 4 步）。
- 测试：`app.zig` 的 P2 三条（完成 → 资产/播放表、取消 → 无泄漏、非音频 → 不建样式），
  用现成的正弦 WAV 生成器 + `std.testing.io`。
- **工程加载**：走**后台解码**（`beginProjectLoadAsync`）——只读头建样式 + 入队，
  时间轴**立刻**可见（片段画"载入 N%"），解码由 worker 陆续完成；状态栏另显示"后台载入音频 (n)…"。
  ⚠️ 单线程 UI 里"弹模态进度窗"是行不通的：解码还在 UI 线程时，窗口消息循环被占住，
  连标题栏都拖不动（实测反馈）——**必须交给工作线程**，进度窗只是可选的 UI 糖。
  未做（后续）：加载期**禁止播放**（用户提到"避免播到不完整的音乐"）可做成一个
  `project_loading` 闸门；小文件同步快路径、占位装饰延迟 150 ms、批量汇总面板。

### P3（未开始）：长文件与内存

> 本节 P1/P2/P3 是**导入性能**分期，与 §11 的功能分期（P1 资产层 / P2 采样器鼓组层 /
> P3 音频片段）**不是一回事**。

**现状（P2 之后）**：解码结果**恒为立体声 f32** = **384 KB/s = 22 MB/分钟**；
峰值 ≤ 32 KB/资产可忽略。5 分钟立体声歌 = 110 MB；30 分钟上限 = 660 MB；
一个工程放 10 首歌 ≈ 1.1 GB。

#### 已作废的条目
- ~~峰值懒计算 / 逐级细化~~：P1 之后峰值与解码是**同一遍**顺带算的（桶大就抽样），
  总开销 ≤ 32 KB/资产。这条源于“峰值要单独跑一趟”，现已不成立，**删除**。

#### P3a（**已实现**）：i16 / 保留单声道 —— 内存 2~4×

**目标**：立体声 16-bit 源 8 B/帧 → 4 B/帧（2×）；单声道源 → 2 B/帧（**4×**）。
**不做**：位深泛化、>2 声道、流式。

**存储布局**（`audio.SampleData`）
- `frames: union(enum) { s16: []const i16, f32: []const f32 }`；
- `channels: u8`（1 或 2）——**保留单声道**，读取时展开到 L/R；
- `frame_count` / `ratio` / `engFrames()` **不变**（仍是原生率帧域）。

**格式选择规则**（导入时定，结果写进 `audio_import.Header`）

| 源 | 存储 | 理由 |
|---|---|---|
| WAV / FLAC，位深 ≤ 16 | s16 | 零损失 |
| WAV / FLAC，位深 24 / 32f | **f32** | 零损失（Sawdust 导出是 24-bit，不能比素材还糙） |
| MP3 / OGG（有损） | s16 | 编码噪底远高于 −96 dB，听不出 |
| 未知容器 | f32 | 安全兜底 |

- 位深来源：WAV 读 `fmt ` 的 `wBitsPerSample`（偏移 34）；FLAC 读 `STREAMINFO` 的
  sample-size（5 bit）。解析失败 → 当“未知容器”。约 60~80 行。
- 声道数来源：把 probe 的 `ma_decoder_config_init(fmt, **0**, 0)` 改成 **channels = 0**
  （= 保留源声道数），再用 `ma_decoder_get_data_format` 读回真实 `ch_out`；
  ≥2 声道一律存 2（5.1 由 miniaudio 下混）。

**统一取样入口**（防“只有右耳”类 bug 复发）
```zig
// audio.SampleData
const k16: f32 = 1.0 / 32768.0;
inline fn frameAt(self: *const SampleData, i: usize) [2]f32;            // 单声道自动双臂
pub inline fn sampleStereoAt(self: *const SampleData, pos: f64) [2]f32; // 线性插值
```
**所有**播放/试听路径只准走 `sampleStereoAt` / `frameAt`，**禁止再出现 `frames[i*2]` 下标**。

**改动点位**（一次性改完，漏一处 = 噪音/单耳）

| 位置 | 现状 | 改为 |
|---|---|---|
| `audio.zig` 1014-1017 采样器层 | 手写 4 下标 + lerp | `sampleStereoAt` |
| `audio.zig` 1599-1608 片段扫描 | lerp / nearest 两分支 | `sampleStereoAt`（t = 0 即 nearest） |
| `audio.zig` 1647-1648 试听 | 直接下标 | `sampleStereoAt` |
| `audio_import.zig` `updatePeaks` | 读 f32 交错 | 走 `frameAt`（从 i16 算，无损失） |
| `audio_import.zig` 109 `probeFile` | `(f32, 2, 0)` | `(f32, 0, 0)` + 读回 `ch_out` + 位深 → `Header` |
| `audio_import.zig` 418 解码 | `(f32, 2, 0)` + `[]f32` | 按 `Header` 计划 `(s16\|f32, 1\|2, 0)` + 对应切片 |
| `audio_import.zig` `Buffers` | `frames: []f32` | `s16: ?[]i16` / `f32: ?[]f32`（过继时清空指针，保持现有防 double-free 手法） |
| `app.zig` 2944 同步导入 | `(f32, 2, 0)` | 同 `Header` 计划 |

**测试清单**
1. 16-bit 立体声 WAV → `frames == .s16`、`channels == 2`、帧数正确、样本值在 1/32768 内与 f32 基线一致；
2. 24-bit WAV → `frames == .f32`、`channels == 2`（零损失）；
3. 单声道 WAV → `channels == 1`、`frames.len == 帧数`、`sampleStereoAt` 左右相等；
4. 立体声 + 声像极左 → 右声道恒 0（**“只有右耳”回归测试**）；
5. 内存断言：16-bit 立体声 4 B/帧、单声道 2 B/帧（`frames.len * @sizeOf`）；
6. 渲染等价：同一夹具改造前后输出差 < 1e-3（片段扫描 / 试听 / 采样器层各一条）；
7. 现有 3 条采样器层渲染测试 + P2 三条导入测试适配后全绿（当前 360 条）。

**收尾**
- 30 分钟闸门改**字节预算**（建议单文件 1 GB / 全工程 2 GB；按 `帧数 × 声道 × @sizeOf` 估），
  或直接放宽到 2 小时；
- 更新本文 §12 测试清单 + README 性能条目。

**风险与退路**
- 每样本多一次 `switch` + i16→f32 转换：**先不优化**；若实测混音 CPU 上升，再按
  （格式 × 声道）拆 4 个专用循环副本。
- 单声道路径漏改的表现是“单耳”或“音量减半”：由 `frameAt` 单点入口 + 测试 3/4 兜住。

**实现备注（与上述计划的差异）**
- 位深探测需要读文件头 → Zig 0.17 的文件 API 必须带 `std.Io`，而 `probeFile` / `decodeAll`
  的调用点（模型层、测试）手上没 io → `audio_import` 内部放了一个惰性初始化的
  `std.Io.Threaded` 单例（`fileIo()`），只做同步 open / read，不触发线程池。
- `ma_decoder_config_init(fmt, **0**, 0)` 实测确实保留源声道数（单声道回来 1）——这条依赖
  成立，否则单声道会被静默上混回立体声。
- 单文件闸门取 **1 GB**（而非分“单文件/全工程”两档）：16-bit 立体声 48k ≈ 91 分钟；
  全工程预算留给 P3b。
- `App.loadAudioAsset` 改为复用 `audio_import.decodeAll()`（删掉约 60 行重复解码逻辑），
  同步/异步两条路现在是**同一份**计划 + 峰值算法 + 宽路径。
- 峰值仍与解码**同一遍**算完（从 i16 直接算，无精度损失）。

#### 多声道（>2）素材的现状：**下混成 2 声道，无限期不做环绕**

当前行为（P3a 之后）：`probeFile` 能问到真实声道数（5.1 → 6、7.1 → 8），但
`Plan.channels` **强制为 2** → miniaudio 在解码器内部做声道转换，存下来的是**立体声下混**。
用的算法是默认的 `ma_channel_mix_mode_rectangular`（`ma_channel_mix_mode_default` 就是它，
见 `miniaudio.h:4353`），权重来自 `g_maChannelPlaneRatios`（`miniaudio.h:54293`）：

| 输入声道 | → 输出 L | → 输出 R |
|---|---|---|
| 前左 FL | **0.5** | 0.25 |
| 前右 FR | 0.25 | **0.5** |
| 中置 FC | **0.5** | **0.5** |
| 环绕 BL/BR | 0.25 / 0 | 0 / 0.25 |
| **LFE** | **0** | **0** |

即 `L = 0.5·FL + 0.25·FR + 0.5·FC + 0.25·BL`。\
三个必须知道的后果：
1. **LFE 完全丢弃**（LFE 无“平面”，权重表全 0）；
2. **不做归一化** → 5.1 全通道同相时 L 可达 1.5（+3.5 dB）、7.1 可达 2.0（**+6 dB**）→
   写回 `s16` 时**硬削波**（miniaudio 不限幅）；
3. 不可逆：存下来的是立体声，环绕信息永久丢失。

**为什么不做环绕（用户拍板，无限期）**：商用 DAW 里很多都不支持，唱片公司发布的音频
绝大多数也是双声道，回报不划算。真要做也**另立项**，分三层：
- **S1（便宜，不动混音器）**：记录源声道数 + UI 标注“5.1”；导入时三选一
  （下混 / 只取 L/R / 取指定一对）+ 下混归一化增益。覆盖 95% 的 stem 导入需求；
- **S2（贵）**：真多声道渲染——总线布局 {2,6,8}，`renderSegment` 里音符合成 / 片段扫描 /
  采样器层 / EQ / 声像 / 电平表 / master **全部**要按布局循环；`wav.zig` 需写
  `WAVE_FORMAT_EXTENSIBLE`；zig-vst3 要能协商 6/8 声道 bus 并在插件只支持立体声时
  插 up/down-mix 桥；存档加“工程输出布局 + 每样式源映射”；混音台 UI 换 2D 声像面板；
- **S3（专业级）**：ITU-R BS.775 风格下混系数、LFE 策略、可切换监听布局。

> 将来真动 S1 时，务必先加下混增益——现在的默认行为在 7.1 热素材上是会削波的。

#### P3b（延后）：热集缓存 / LRU 逐出
- 已解码资产保留在预算内（如 512 MB），其余**只留峰值（≤ 32 KB）+ 路径**；
- 冷资产要播时复用 `audio_import` 的 worker 后台重解，期间静音（几十 ms）；
- 释放必须走现有“旧播放表退役不释放”手法（`retired` 列表），否则音频线程 UAF；
- 价值：工程里放 20 首歌也不爆内存；代价：中（多一层生命周期状态机）。
- **暂不做**：等真出现“工程里塞很多长文件”再上。

#### 流式播放（**暂不做**，遥远未来）
- 收益：内存从 O(时长) 降到 O(预读几秒)，并能“只解用到的区段”（现在 trim 出 2 秒也一样整段解）；
- 不做的理由：
  1. `ma_decoder_seek_to_pcm_frame` 对 MP3 / Vorbis 要从前一个 seek point 重解 →
     用户频繁拖游标时**体验反而变差**；
  2. 音频线程绝不能等磁盘 → 需要额外 IO 线程 + 环形缓冲 + “样本没到位”策略；
  3. 同一素材多声部（两片段 + 采样器同时打）各需预读缓存；
  4. 与 `speed 0.5..2.0`、trim 区间循环、loop restart 的样本偏移全部要重算；
  5. 现架构是**不可变指针快照**（`AudioTableRow.asset: ?*const SampleData`），流式要把它
     换成每声部的管道状态 —— 是这几项里**改动最大、风险最高**的。
- 结论：P3a + 字节闸门已够用；真需要 1 小时素材时再评估。
