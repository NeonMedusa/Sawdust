# 音符 / 片段命中判定（鼠标到底点中了什么）

> 状态：**已实现并定稿**（2026-11，手感经用户实机确认）。
> 相关代码：`src/view_pianoroll.zig`（`note_hit_tol_px` / `noteAtMousePx`）、
> `src/view_playlist.zig`（`hitAt` / `sinkClipToTieBottom`）。
> 相关文档：`docs/drag-snap.md`（拖动的量化规则）、`docs/note-lane.md`（下方力度/声像轨）。

---

## 1. 一句话

**命中按"像素邻近"判定，不按 `(音高, 步)` 精确匹配。**
鼠标落点取**最近的对象**；而"最近"的窗口 = 对象本体（至少 1px）**向外扩 4px**。

## 2. 旧判据为什么必然坏

旧实现按 `(pitch, step)` 精确匹配——即"鼠标所在的**整格**里必须有一个起点正好在这里的音符"。

- 每步像素 `util.pianoStepPx()` = **0.125 px**（`piano_whole_note_px = 480` / 3840 步）；
- 一个 **1 步长**的音符在 100% 缩放下只有**1px 宽**（`floor(0.125) → 1`）；
- 格子的横向宽度也是 1px 级别 → 命中要求鼠标落在那个 1px 上。

实测后果：窄音符在 `zoom ≤ 8` 时**大部分位置永远点不中**，hover / 按下拖动 / 右键擦除
**全部失效**（用户实症：画完 1/64 的音符，回头怎么点都点不到）。

> 教训：**缩放让几何缩到亚像素时，"精确几何命中"必然失效**。
> 命中判定要用**像素容差**，而不是把宽容度塞进数据坐标。

## 3. 现行判据（`noteAtMousePx`）

```zig
const note_hit_tol_px: f32 = 4.0;

// 候选：矩形相交（本体至少 1px，四边各外扩 tol）
// 排序：**中心距离最近**者胜
// 等距：取**数组序更大**者（= 后画的 = 顶层，与 `topmostNoteAt` 的「叠放取顶层」一致）
```

- 只考虑 `pattern == app.piano.pattern` 且 `instrument == app.sel.instrument` 的音符
  （与画卷帘、框选、Del、Ctrl+M、Ctrl+Q 完全同一收窄口径）；
- 返回的是**数组下标**，调用方不要再用 `(pitch, step)` 反查（那正是旧 bug 的形状）。

### 3.1 边缘热区与命中模式

命中之后还要判"点在音符的哪个部位"（决定是移动还是拉伸），实现在
`view_pianoroll.noteHitMode(nx, nw, mouse_x)`。**分两档，保证任意宽度下三区都在**：

| 音符本体宽 | 左 `.left`（拉伸左端） | 中 `.body`（移动） | 右 `.right`（拉伸右端） |
|---|---|---|---|
| ≥ 24px（常规） | 左侧 8px（＋外侧 4px 容差） | 中间全部 | 右侧 8px（＋外侧 4px 容差） |
| < 24px（窄） | 命中窗口左 ⅓ | 中 ⅓ | 右 ⅓ |

> **"命中窗口"** = 音符本体 ± `note_hit_tol_px`（4px）。最窄的音符（1px）也有 **9px** 窗口
> → 左/中/右各 3px：从左边靠近能拉左端，正中间（压在音符上）能整条拖走，从右边靠近能拉右端。
>
> 旧实现（两侧都到 8px 就"按相对位置就近选一侧"）在窄音符上会把 `.body` 完全挤掉——
> 中部永远命中不到（实测：短音符只能拉、拖不动）。现在改成三等分，三者共存。

分界点选 **24px = 3 × 热区**：低于这个宽度两道 8px 热区就会重叠，中间不可能留出移动区。

单测：`pianoroll: 命中分区——极短音符也有左/中/右三段`——除了具体像素断言，还对
**宽度 1..64px 逐像素穷举**，断言三区都存在且只能按“左 → 中 → 右”出现（不交叉）。

### 3.2 必须走它的五个入口

```
hover 高亮 / 左键按下 / 拖动（含批量） / 右键擦除 / Ctrl+Shift 切换选中
```

**新增任何"指到某个音符"的交互，都必须复用 `noteAtMousePx`。**
各写一套 `(pitch, step)` 精确匹配 = 直接复活本节的 bug。

### 3.3 框选优先

`ui.mods_ctrl` 按下时（要开始框选）以及框选进行中，**完全不做音符命中**：

- 否则框选起点会先选中/拖走一个音符；
- 表现就是"想划个框，结果音符先飞了"。

## 4. 同一帧里的时序：`px_per_step` / `drag_steps` 必须在按下**之后**算

这是与命中相邻的另一个坑（同一次修复里抓出来）：

```
按下处理：记录 drag_down_x、决定命中/放置……
之后才能算 px_per_step / drag_steps
```

旧代码在按下处理**之前**用 `drag_down_x` 算位移——那一帧拿的是**上一次手势**的旧锚点。
100% 缩放下 1px = 8 步，480px = 3840 步 = **整整一小节**，于是：

> 表现：新放的音符**先出现在别处**，下一帧才"瞬移"到鼠标下。

**任何"按下即创建"的交互都要检查：算几何用的锚点是不是本帧刚写的那一个。**

## 5. 调 `note_hit_tol_px` 的判据

| 值 | 效果 |
|---|---|
| **4.0**（现行） | ≈ 半个行高（`piano.key_h` 默认 8~12px 一档），实测顺手；密集和弦也不会点错行 |
| < 2 | 等于退化成"精确命中"，窄音符又点不中了 |
| > 8 | 开始**抢到邻行**音符（上下各一行都能命中），和弦密集时选错音 |

改这个值只需要改一个常量，但**改完必须实机验**：1 步音符 hover、右键擦除、窄音符左右缘拉伸、
窄音符**中间仍能拖动**（三等分窗口会随容差变宽）。

## 6. 播放列表侧的对应规则（片段命中）

同一套"像素邻近 + 部位判定"的思路，实现在 `view_playlist.zig`（`clipAtMousePx` / `clipHitMode`）：

| 判定 | 规则 |
|---|---|
| **本体** | 片段矩形（`clipXW`；至少 1px 宽） |
| **命中窗口** | 本体 ± `clip_hit_tol_px`（**4px**）——1 步的小片段在低缩放下只有 1px，没容差就站不上去 |
| **分区** | 与音符**同一套两档规则**：≥ 24px → 左右各 8px 边缘；< 24px → 命中窗口**三等分**（左 ⅓ 拉左缘 / 中 ⅓ 移动 / 右 ⅓ 拉右缘） |
| **先精确后容差** | 鼠标**落在片段所占的步上** → 仍走老的 `topmostClipAt`（叠放取顶层，**手感与连点轮换零变化**）；只在“偏出去”时才走像素容差，取**中心最近**者、等距取更上层 |
| **竖直方向** | 按轨道行（`track_h`）判定，行轴向下无上界 |
| **叠放**（同左端点/重叠） | 点中即 **沉到同左端点组的最底层**（`sinkClipToTieBottom`），连点即轮换——这样重叠的片段都能点到 |
| **双击** | 打开该片段（PAT 模式进场） |
| **Ctrl 按下** | 不做片段命中（框选优先），与音符一致 |

> 右键擦除也用**命中片段自己的 (轨道, 左端步)** 去套 `eraseClipsAt`（与钢琴卷帘的音符擦除同一套写法）
> ——像素命中只负责“指向哪个片段”，叠放语义不变。

> 与音符的差别：片段的左缘拉伸改的是 `offset` / `trim_start`（**内容头跟着折开**，
> 内容在时间轴上不动），不是起点的简单平移；其余（热区、容差、三区）两边完全对称。

## 7. 验收清单（改命中相关代码后必跑）

1. **1 步长**音符：hover 有高亮、按下能拖、右键能擦；
2. **密集和弦**（同列 5 个音高）：点哪个中哪个，不串行；
3. 窄音符（含缩到 **1px**）：左侧能拉左端、中间能拖动、右侧能拉右端，三者不打架；
4. 缩放 25% / 100% / 800% 各试一次（亚像素与超大两个极端）；
5. `Ctrl+拖` 框选：起点落在音符上也**不**先选中/拖走音符；
6. 放置音符（单击）后**第一帧**就出现在鼠标位置（不瞬移）；
7. 播放列表：重叠片段连点能轮换到每一层；缩放后仍可点中 **1 步小片段**——且它左右两侧能拉边、中间能拖。
