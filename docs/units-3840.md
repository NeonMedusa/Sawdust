# 时间分辨率迁移：U = 96 → 3840（24 → 960 PPQN）

> 状态：**进行中**（本文即迁移清单，边改边勾）。
> 动机：96 步/全音符（= 24 PPQN）做不出 1/64、1/128 网格，独立钢琴引擎时期的
> "1/96 太粗"就是这个限制；自动化曲线也需要更细的坐标。
> 目标值 **3840 = 960 PPQN**（主流 DAW 的常见上限档）。

## 0. 术语

| 说法 | 含义 |
|---|---|
| **U** / `units_per_whole` | 每个**全音符**的步数（结构性常量，全工程唯一坐标单位） |
| **PPQN** | 每个**四分音符**的步数 = `U / 4`（4/4 下） |
| 步 | 最小时间单位；`1 步 = 1/U 全音符`。120 BPM 下 1 步 ≈ 0.52 ms（U=3840） |

## 1. 为什么选 3840

主流 DAW 的内部时间分辨率大致落在 **480 ~ 960 PPQN**（少数默认 96、可调高；960 通常是上限档）。
我们的旧值是 **24 PPQN**（96 步/全音符），远低于这个区间——连 1/64 网格都表示不了；
本次提到 **960 PPQN**（3840 步/全音符），一步到位进入主流区间。

整除性：3840 = 2⁸·3·5 → 支持 1/64、1/128、1/192、1/384、1/960、1/3840 网格，
**五连音精确**（3840/5 = 768）；7 / 11 连音为亚毫秒近似（与主流 DAW 相同——它们
同样做不到整数 tick）。**不做**：把 U 拉到 13440 以上换 7/11 整数精度（快照内存爆炸）。

### 2.5 过程中发现的额外真问题（已一并修）

1. **导出时长被截短**（U=3840 后误差从 0.1% 放大到 2~4%）：`exportAudioBegin` 原本
   “每步取整成整数帧，再 × 步数”。改为 **f64 帧/步先乘后取整**（`step_frames_f`）。
2. **`App.framesPerStep()` 读的是给音频线程的原子镜像**（`params.steps_per_beat`，由 main 每帧同步）——
   测试/非帧循环路径下它可能是旧值，与 `audioClipAdd` 等处相差 40 倍。改为**直接用 model 推导**。
3. **小数 BPM 的“步宽变化”被取整吃掉**（25 帧/步的量级下 120 vs 120.5 不足半帧）：
   该测试改为校验**未取整的 f64 帧/步**（`audio.stepFramesOf`）。
4. **`steps_per_bar` 冗余字段让整张时间轴错 40 倍**（实测：启动后一屏看到 **70 小节**
   而不是 7 小节）：这是存进存档的值，拍号的派生物，而迁移时只按 `== 96` 换 →
   3/4 工程（旧值 72）或任何异常值都漏换 → `bar_w = spb×480/U` 变成 9px/小节。
   修法两层：① 迁移里**一律 ×40**（它也是步域）；② **加载侧完全不信它**——
   `importProject` / `applyHistoryState` 直接 `model.stepsPerBarFor(time_num, time_den)` 推导。
   （教训：“由别的字段派生的冗余字段”永远不要当数据读，推导即可。）
5. **`muted` 的引入版本曾写成“当前版本”**：`introducedVersion` 里
   `return binary_version;`（当前= 8）——一旦把 `binary_version` 抬到 9，
   `muted` 的引入版本也跟着飘到 9 → **旧 v8 档读时会被当作“无此字段”跳过 → 字节流错位**。
   修法：钉死 `binary_version_v8 = 8`（与 v6 同一种写法），并在新测试里用
   “写当前版本字节 → 把版本字节改回 8 再读”模拟旧档，专门盯住这一路。
6. **“缩到上万小节 + 乱涂乱画” → `integer overflow` panic**（`view_pianoroll.zig` 的
   `mouseLocalStepSnap`）：`raw = cpx * spb / bar_w` 里的 `cpx * spb` 是 i32 乘积。
   缩得足够小时内容像素 `cpx` 可达数十万，× `spb`（3840）直接冲出 i32
   （U=96 时要 40 倍那么远才触发，所以以前碰不到）。
   已修为 **i64 中间值 + 上限 2^28 步**（≈ 7 万小节，留给 `snapRound` 的 `+半格` 余量）。

### 实机验收阶段发现并已修的问题

1. **一屏看到 70 小节（缩放不对）**——`steps_per_bar` 冗余字段未迁移/不可信。
   已修：迁移一律 ×40；加载侧由拍号推导（两边都不留余量）。
2. **点击播放后 `integer overflow` panic**（`view_playlist.zig` 的音符预览）：
   `@divTrunc(s * inner_w, win_steps)` ——**步数 × 像素宽**的 i32 乘积。
   U 变成 40 倍后，放大 8× 时 `s` 与 `inner_w` 都能到十几万 → 乘积溢出。
   已修为 i64 中间值，并给 `win_steps` 兜底（防除零）。
   **一类隐患**：凡“步 × 像素”的整数乘法都要 i64——新增该类代码时直接上 i64，别靠 i32。
