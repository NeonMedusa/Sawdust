# 调度与释音协议（Scheduler & Note-Release Protocol）

> 本文描述**播放中编辑**这条链路的协议、不变量与已知边界。
> 改动调度（`sequencer.zig`）、音频分发（`audio.zig`）、静音/拖动释音（`app.zig` 的 `release*`）
> 之前请先读本文，尤其是 §2 的不变量与 §6 的"入口门控表"。

---

## 1. 一句话模型

```
UI 线程：clips/notes ──(前瞻窗口)──► 无锁环形队列 ──► 音频线程：stash → 到点分发 → 声部/插件
                     ▲                                        │
                     └────── 回传：正在发声的音高位图 ◄────────┘
```

- **UI 线程是"大脑"**：算事件、作废、重扫；
- **音频线程是"真相"**：声部状态、插件收发；
- 两者**没有任何互斥锁**，只经 无锁环 + 原子量 通信；
- 音频线程**零分配、零 I/O、零阻塞**。

---

## 2. 不变量（违反即产生"挂音/误切"）

1. **每个 note-on 最终恰好被释放一次**（早、晚都不行）。
2. 释放必须**按实例**（或至少按"起点步 + 音高 + 乐器"精确）——同音高多实例是合法的。
3. 传输层**允许丢事件**（音频线程不能阻塞），因此"**必须送达**"的东西**不能**只依赖传输层。
4. 任何"自愈/兜底"必须**可观测**（计数、日志），并且**可以关掉**——否则会掩盖回归。

> 第 3 条是本项目的血泪结论：note-off 早期只走"允许丢"的通道，
> 一旦在重扫/丢弃里丢掉，声部就永远收不到释放（表现为长音不释、或只响音头）。

---

## 3. 事件的形态与生命期

### 3.1 `on` 事件携带 `end_step`

```zig
SchedEvent{
    kind = .on,
    pitch, instrument,
    step      = 音符在歌曲时间轴上的起点,
    on_step   = 同一值（供 off 精确匹配用）,
    end_step  = 该音符**应该在**哪一步结束,   // ← 关键
    velocity, pan, gen, edit_gen,
}
```

`end_step` 有两个用途：

1. **结构性的释音保障**（见 3.2）；
2. **不变量自检**（见 §5）。

### 3.2 本地到点释音（方案 B）

音频线程每块检查每个正在发声的声部：

```zig
if (voice.end_step >= 0 and cur_step >= voice.end_step) → 本地发 off
```

- 覆盖：内置合成器声部池、鼓组 synth 层池、**VSTi**（按宿主位图 + `Engine.vsti_end`）；
- 关键性质：它**在音符自己的结束点**生效，正常长音永远不会被提前切；
- 因此"丢一条 off"的最坏后果从**永久挂音**降级为**晚到一个块边界**（≤ 数毫秒）。

### 3.3 传输层仍然发 off

`gatherRange` 继续发射 `off`，作用变成"**精确定时**（精确到音频帧）+ **提前终止**"。
它丢了也不会挂音（3.2 兜住），所以不需要为它设计复杂的一致性规则。

> 曾评估"彻底删掉传输层 off"：净删代码约 10 行，但会把释放精度从"帧"退化到"块"，
> 且需要重写十余个以 off 为题的测试 —— **收益不足，不做**。

### 3.4 `gen` 与 `edit_gen`

| 字段 | 何时变化 | 音频侧后果 |
|---|---|---|
| `gen`（传输代） | 起播 / 停止 / 跳转 / 循环回跳（`reset`） | 整批作废 + **释放全部声部**，随后按新起点重发跨起点长音 |
| `edit_gen`（编辑代） | 播放中重扫（见 §4） | 旧代事件作废；旧代 `on` 一律丢，旧代 `off` 只丢"重扫覆盖段内"的 |

作废规则（`audio.schedEventObsolete`）：

```
gen 不符              → 作废
edit_gen 是当前代      → 保留
step < rescan_from     → 保留（重扫没覆盖这段，正常触发一次）
否则（旧代的 on/off）  → 作废（重扫已按新数据重发）
```

## 4. 播放中编辑：窗口与重扫

### 4.1 窗口

- 前瞻窗口：`[scheduled_upto, 当前步 + 4 小节)`，UI 每帧推进（**每帧最多 16 步**，
  避免一次性推入上千条把音频侧 `stash` 挤爆）；
- 重扫时只重发**受限的一段**：`max_rescan_steps = 96`，其余交回前瞻补齐。

### 4.2 安全界（`rescan_from`）

重扫的起点是"音频线程**确定还没走到**的第一步"（音频位置 + 余量），
而不是"UI 游标 + 1"——UI 游标落后于音频位置，从游标起会把音频**已经触发过**的 on 再发一次，
造成双声部，而 off 只有一份 → 个别声部悬挂。

### 4.3 **要不要重扫**：窗口指纹判据

比"片段数组有没有变"更准、也更省：

```zig
scheduleWindowUnchanged()  // 比较 [cur, scheduled_upto) 内"可闻 on 事件"的指纹
                           // （数量 + 顺序无关哈希）
```

由此得到统一语义：

| 编辑 | 窗口内可闻 on 变了吗 | 重扫 |
|---|---|---|
| 远处增删/拖动片段 | 没变 | **不扫** |
| 拖进/出静音轨、拖不可闻片段 | 没变 | **不扫** |
| 静音开关（窗口内有它的 on） | 变了 | 扫 |
| 游标下增删/拖动/改力度/声像 | 变了 | 扫 |

理由：重扫会把整段窗口的旧事件作废并重发（音频线程要逐条插入 `stash`），
在密集工程里是**毫秒级尖峰**，会让正在播的其它轨"卡一下"。窗口外的编辑**本来就不该惊动音频线程**。

## 5. 诊断

启动参数：`--sched-log`（每秒一行汇总 + 落盘）、`--sched-log=2`（另加逐条明细）。
日志：`<exe 目录>/data/logs/sched.log`（滚动的，超 256KB 只保留后半）。

汇总行关键字段：

| 字段 | 含义 |
|---|---|
| `作废 on/off` | 旧代事件被丢弃的数量（重扫导致，正常） |
| `off超前[min,max]` | 被丢弃的 off 距当前步多远（接近 0 = 在播放头眼皮底下被丢） |
| `stash满 / vsti满 / 队列满` | 三处静默丢弃，**应为 0** |
| `积压 stash/队列` | 待触发事件积压（stash 容量 2048） |
| **`本地off`** | 本地到点释音生效次数（>0 说明传输层 off 确实丢过，被兜住了） |
| **`超时=当前/峰值 迟到=N步`** | **不变量自检**：过了 `end_step` + 1 小节还在发声的声部数。**必须恒为 0** |
| `[long] inst= kind= pitch= start= len= hung= off_seen= pend=` | 单次发声画像（时长、是否收到 off、队列里还有没有 off） |

`超时` 非 0 就说明协议被破坏了 —— 这是回归的第一判据（比"听起来有没有卡"可靠得多）。

## 6. 释音入口门控表（改这里之前先看）

| 入口 | 做什么 | 门控 |
|---|---|---|
| 播放列表 Ctrl+M（片段静音） | 释音 + 可能重扫 | `App.toggleClipMute` → `muteNeedsRescanForClips(.clip)` |
| 轨道静音按钮 / 解静音 | 同上（该轨全部片段） | `muteNeedsRescanForClips(.track)` |
| 钢琴卷帘 Ctrl+M（音符静音） | 同上（按音符） | `App.toggleNoteMute` → `muteNeedsRescanForNotes` |

> ⚠️ **另一层静音已经把片段弄哑时，不要再为它重扫**：切**轨道**静音时跳过"自身已静音"的片段；
> 切**片段**静音时跳过"所在轨已静音"的片段（`MuteToggle` 参数就是干这个的）。
> 否则"切一个本来就哑的片段所属轨的开关"会让**其它轨**整窗重发 → 实测"track1 卡一下"。
>
> ⚠️ **静音门控必须双向**：释音只看"刚变成静音"的对象，但**重扫门控要看"全部被切换"的对象**。
>
> ⚠️ **静音切换的重扫必须"全段"**（`muteTrackLiveFull`，不受 `max_rescan_steps` 限窗）：
> 被限窗落下的事件**没有替代品**（前瞻不会回头）→ 取消静音后音符永远不响。
> 而且它**只扫一次**：`commitHistory` 随后那次"编辑重扫"要跳过（`skip_next_edit_rescan`），
> 否则第二次会把第一次刚发的、位于限窗之外的 `on` 判为旧代丢掉。
>
> ⚠️ **不要用"补一条 on"来修**：窗口里本来已排好的那条不会被撤掉，
> 两条同 `(音高, 起点步)` 的 on 在**内置合成器**上是无害的（会先放旧再起新），
> 但对 **VSTi** 就是**两个 note-on 叠在一起** —— 实测表现为"每切两次静音，整曲音量高一层"。
> 曾经只把"刚静音的"喂给门控 → **取消静音永远不重扫** → 窗口里那段被当作静音发过（没有 on），
> 而前瞻是单向的，于是音符扫过去是哑的（song 模式必现；PAT 模式因门控保守返回 true 而侥幸正常）。
| 拖动/拉伸提交（位置变化） | 释音 + 重扫 | `syncDragSnaps` + `muteNeedsRescanForClipMove` |
| 拖动换轨（进出静音轨） | 释音 + 重扫 | `muteNeedsRescanForClipMove` |
| 任意编辑提交（历史） | 可能重扫 | `scheduleWindowUnchanged`（窗口指纹） |

静音语义：**以后不再触发 + 此刻正在响的立即释音**（不是"等它响完"）。

## 7. 复杂度与已知上限

- `gatherRange` / 差分重扫都是 **O(片段数 × 音符数)**；
- 门控类判定是它的**子集**（只扫受影响片段），所以门控永远不比重扫贵；
**索引化方案（先量、再决定，暂未实施）**

现状：`gatherRange` / 差分重扫 / 窗口指纹都是 `O(片段数 × 音符数)` 的全扫描，
与"这一步真正要处理多少事件"无关（内层绝大多数 `nt.pattern != clip.pattern` 直接 continue）。

| 索引 | 做法 | 消掉的浪费 |
|---|---|---|
| 音符按样式分组 | `pattern → []note`（编辑后**懒重建**，O(N)） | 内层的样式过滤（通常 99%） |
| 片段按样式分组 | `pattern → []clip` | 外层只遍历该样式的片段 |
| 窗口活跃集 | 片段按 `start` 排序 + 维护"与 `[from,to)` 相交"的集合 | 远处片段完全不参与（注意：重扫会**回退**窗口，必须支持重建） |

- 效果：`O(片段 × 音符)` → `O(活跃片段 × 该样式音符)`，通常降 1~2 个数量级；
- **它不改善音频稳定性**（那些扫描在 **UI 线程**），改善的是"大工程的 UI 跟手度 / 重扫耗时"，
  以及降低"UI 卡顿饿死前瞻"的风险；
- **先量后做**：加一个"每帧调度耗时（平均/峰值 µs）"计数器，判定阈值：
  `<1ms` 不做；`1~4ms` 只做"按样式分组"；`>4ms` 或片段数 >1000 再上"窗口活跃集"；
- **风险**：索引必须在每次增删改后失效。做法是 **dirty 版本号 + 懒重建**，
  **不要**做增量维护（那是幽灵音符的温床）。
- `audio.stashInsert` 每条 **O(n)**（同键去重 + 有序插入）。重扫限窗后尖峰已显著降低；
  若将来仍见掉块，可改为"批量排序后一次归并（O(n+m)）"。

## 8. 回归测试

| 测试 | 保护的不变量 |
|---|---|
| `sched_stress.zig`：`sched stress (synth)` / `(VSTi)` | 随机拖动/静音 + 安全界抖动 + 同帧两次重扫，6000 块音频后 **`overrun == 0`** |
| `synth: note-off 按起点步精确匹配…` | 释音不误切同音高别的实例；同实例重触发不产生双声部 |
| `sched: 释音不误杀——切一个实例不得连带另一个同音高实例` | **端到端**：同一样式两条轨（起点 0 / 8），切掉起点 8 的实例后，起点 0 的声部必须仍在响（若退化成按音高 FIFO，此测试会失败——已验证） |
| `sequencer: 静音音符 on / off 都不发` | 静音内容不产生事件（避免误切其它轨同音高声部） |
| `app: 拖动静音轨里的片段不触发重扫` 等三条 | 不可闻/远期编辑不惊动音频线程（避免掉块） |

## 9. 变更史（教训）

| 曾经的做法 | 结果 |
|---|---|
| off 只走传输层 | 丢一条 = 永久挂音 |
| 静音内容"只跳过 on、off 照发" | off 按音高匹配 → 切掉**其它轨**同音高声部 |
| "off 永不作废" | 旧 off 在旧位置触发 → 新起的音只响音头 |
| 按 (音高, 乐器) FIFO 释音 | 同音高多实例时切错 |
| 各种"看着像挂了就补一条 off"的兜底 | 掩盖真 bug，且会砍合法长音 |
| **现在的做法** | on 带 `end_step` + 本地到点释音（结构性）+ 传输层 off（精确定时）+ 窗口指纹门控（避免无谓重扫） |
> 另记：**"补事件"式的修复对 VSTi 是危险的** —— 它没有声部模型，重复的 note-on 就是叠声部
> （实测：每切两次静音，整曲音量高一层）。凡是要"补"的地方，先想清楚目标音源是否幂等。
>
> 另记：**重扫门控的方向性**也曾出错 —— 只把"刚变成静音"的对象喂给门控，
> 导致"取消静音不重扫 → 音符扫过是哑的"。凡是"切换某状态"的操作，
> 门控与释音所需的集合**不一定相同**，别复用同一个 scope。

**收尾结论（2026-11，日志实证）**：静音切换路径上的"无谓重扫"已全部消灭 ——
`--sched-log` 下每次切换都能看到 `[mute] clips/track … rescan=false` 且
`[hist] … windowUnchanged=true`（即**完全没有调度工作**）。
若此时**仍有**轻微卡顿，那它已不在调度域，而属于实时性/UI 争用（见 §10 末尾与 `docs/linux.md` 的 xrun 待办）。
