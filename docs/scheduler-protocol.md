# 调度与释音协议（Scheduler & Note-Release Protocol）

> 本文描述**播放中编辑**这条链路的协议、不变量与已知边界。
> 改动调度（`sequencer.zig`）、音频分发（`audio.zig`）、静音/拖动释音（`app.zig` 的 `release*`）
> 之前请先读本文，尤其是 §2 的不变量与 §6 的"入口门控表"。
>
> ⚠️ **当前状态（2026-11）**：§1–§9 描述的是**已退役**的 push 模型（UI 推事件 + 前瞻 + 重扫），
> 保留作历史与对照；**现在真正在跑的是 pull 模型**（快照驱动 + 换代对账），
> 见 **§11.8「现行模型（pull）」**。§10 是这次改造的架构审计（为什么要改）。
> 想在调度上再打补丁之前，先看 §11.8 的不变量与 §10.3 的根因。

---

## 1. 一句话模型

```
UI 线程：clips/notes ──(前瞻窗口)──► 无锁环形队列 ──► 音频线程：stash → 到点分发 → 声部/插件
                     ▲                                        │
                     └────── 回传：正在发声的音高位图 ◄────────┘
```

- **UI 线程是"大脑"**：算事件、作废、重扫；
- **音频线程是"真相"**：声部状态、插件收发；
- 两者**没有任何互斥锁**，只经 无锁环 + 原子量 通信；
- 音频线程**零分配、零 I/O、零阻塞**。

---

## 2. 不变量（违反即产生"挂音/误切"）

1. **每个 note-on 最终恰好被释放一次**（早、晚都不行）。
2. 释放必须**按实例**（或至少按"起点步 + 音高 + 乐器"精确）——同音高多实例是合法的。
3. 传输层**允许丢事件**（音频线程不能阻塞），因此"**必须送达**"的东西**不能**只依赖传输层。
4. 任何"自愈/兜底"必须**可观测**（计数、日志），并且**可以关掉**——否则会掩盖回归。

> 第 3 条是本项目的血泪结论：note-off 早期只走"允许丢"的通道，
> 一旦在重扫/丢弃里丢掉，声部就永远收不到释放（表现为长音不释、或只响音头）。

---

## 3. 事件的形态与生命期

### 3.1 `on` 事件携带 `end_step`

```zig
SchedEvent{
    kind = .on,
    pitch, instrument,
    step      = 音符在歌曲时间轴上的起点,
    on_step   = 同一值（供 off 精确匹配用）,
    end_step  = 该音符**应该在**哪一步结束,   // ← 关键
    velocity, pan, gen, edit_gen,
}
```

`end_step` 有两个用途：

1. **结构性的释音保障**（见 3.2）；
2. **不变量自检**（见 §5）。

### 3.2 本地到点释音（方案 B）

音频线程每块检查每个正在发声的声部：

```zig
if (voice.end_step >= 0 and cur_step >= voice.end_step) → 本地发 off
```

- 覆盖：内置合成器声部池、鼓组 synth 层池、**VSTi**（按宿主位图 + `Engine.vsti_end`）；
- 关键性质：它**在音符自己的结束点**生效，正常长音永远不会被提前切；
- 因此"丢一条 off"的最坏后果从**永久挂音**降级为**晚到一个块边界**（≤ 数毫秒）。

### 3.3 传输层仍然发 off

`gatherRange` 继续发射 `off`，作用变成"**精确定时**（精确到音频帧）+ **提前终止**"。
它丢了也不会挂音（3.2 兜住），所以不需要为它设计复杂的一致性规则。

> 曾评估"彻底删掉传输层 off"：净删代码约 10 行，但会把释放精度从"帧"退化到"块"，
> 且需要重写十余个以 off 为题的测试 —— **收益不足，不做**。

### 3.4 `gen` 与 `edit_gen`

| 字段 | 何时变化 | 音频侧后果 |
|---|---|---|
| `gen`（传输代） | 起播 / 停止 / 跳转 / 循环回跳（`reset`） | 整批作废 + **释放全部声部**，随后按新起点重发跨起点长音 |
| `edit_gen`（编辑代） | 播放中重扫（见 §4） | 旧代事件作废；旧代 `on` 一律丢，旧代 `off` 只丢"重扫覆盖段内"的 |

作废规则（`audio.schedEventObsolete`）：

```
gen 不符              → 作废
edit_gen 是当前代      → 保留
step < rescan_from     → 保留（重扫没覆盖这段，正常触发一次）
否则（旧代的 on/off）  → 作废（重扫已按新数据重发）
```

## 4. 播放中编辑：窗口与重扫

### 4.1 窗口

- 前瞻窗口：`[scheduled_upto, 当前步 + 4 小节)`，UI 每帧推进（**每帧最多 16 步**，
  避免一次性推入上千条把音频侧 `stash` 挤爆）；
- 重扫时只重发**受限的一段**：`max_rescan_steps = 96`，其余交回前瞻补齐。

### 4.2 安全界（`rescan_from`）

重扫的起点是"音频线程**确定还没走到**的第一步"（音频位置 + 余量），
而不是"UI 游标 + 1"——UI 游标落后于音频位置，从游标起会把音频**已经触发过**的 on 再发一次，
造成双声部，而 off 只有一份 → 个别声部悬挂。

### 4.3 **要不要重扫**：窗口指纹判据

比"片段数组有没有变"更准、也更省：

```zig
scheduleWindowUnchanged()  // 比较 [cur, scheduled_upto) 内"可闻 on 事件"的指纹
                           // （数量 + 顺序无关哈希）
```

由此得到统一语义：

| 编辑 | 窗口内可闻 on 变了吗 | 重扫 |
|---|---|---|
| 远处增删/拖动片段 | 没变 | **不扫** |
| 拖进/出静音轨、拖不可闻片段 | 没变 | **不扫** |
| 静音开关（窗口内有它的 on） | 变了 | 扫 |
| 游标下增删/拖动/改力度/声像 | 变了 | 扫 |

理由：重扫会把整段窗口的旧事件作废并重发（音频线程要逐条插入 `stash`），
在密集工程里是**毫秒级尖峰**，会让正在播的其它轨"卡一下"。窗口外的编辑**本来就不该惊动音频线程**。

## 5. 诊断

启动参数：`--sched-log`（每秒一行汇总 + 落盘）、`--sched-log=2`（另加逐条明细）。
日志：`<exe 目录>/data/logs/sched.log`（滚动的，超 256KB 只保留后半）。

汇总行关键字段：

| 字段 | 含义 |
|---|---|
| `作废 on/off` | 旧代事件被丢弃的数量（重扫导致，正常） |
| `off超前[min,max]` | 被丢弃的 off 距当前步多远（接近 0 = 在播放头眼皮底下被丢） |
| `stash满 / vsti满 / 队列满` | 三处静默丢弃，**应为 0** |
| `积压 stash/队列` | 待触发事件积压（stash 容量 2048） |
| **`本地off`** | 本地到点释音生效次数（>0 说明传输层 off 确实丢过，被兜住了） |
| **`超时=当前/峰值 迟到=N步`** | **不变量自检**：过了 `end_step` + 1 小节还在发声的声部数。**必须恒为 0** |
| `[long] inst= kind= pitch= start= len= hung= off_seen= pend=` | 单次发声画像（时长、是否收到 off、队列里还有没有 off） |

`超时` 非 0 就说明协议被破坏了 —— 这是回归的第一判据（比"听起来有没有卡"可靠得多）。

## 6. 释音入口门控表（改这里之前先看）

| 入口 | 做什么 | 门控 |
|---|---|---|
| 播放列表 Ctrl+M（片段静音） | 释音 + 可能重扫 | `App.toggleClipMute` → `muteNeedsRescanForClips(.clip)` |
| 轨道静音按钮 / 解静音 | 同上（该轨全部片段） | `muteNeedsRescanForClips(.track)` |
| 钢琴卷帘 Ctrl+M（音符静音） | 同上（按音符） | `App.toggleNoteMute` → `muteNeedsRescanForNotes` |

> ⚠️ **另一层静音已经把片段弄哑时，不要再为它重扫**：切**轨道**静音时跳过"自身已静音"的片段；
> 切**片段**静音时跳过"所在轨已静音"的片段（`MuteToggle` 参数就是干这个的）。
> 否则"切一个本来就哑的片段所属轨的开关"会让**其它轨**整窗重发 → 实测"track1 卡一下"。
>
> ⚠️ **静音门控必须双向**：释音只看"刚变成静音"的对象，但**重扫门控要看"全部被切换"的对象**。
>
> ⚠️ **静音切换的重扫必须"全段"**（`muteTrackLiveFull`，不受 `max_rescan_steps` 限窗）：
> 被限窗落下的事件**没有替代品**（前瞻不会回头）→ 取消静音后音符永远不响。
> 而且它**只扫一次**：`commitHistory` 随后那次"编辑重扫"要跳过（`skip_next_edit_rescan`），
> 否则第二次会把第一次刚发的、位于限窗之外的 `on` 判为旧代丢掉。
>
> ⚠️ **不要用"补一条 on"来修**：窗口里本来已排好的那条不会被撤掉，
> 两条同 `(音高, 起点步)` 的 on 在**内置合成器**上是无害的（会先放旧再起新），
> 但对 **VSTi** 就是**两个 note-on 叠在一起** —— 实测表现为"每切两次静音，整曲音量高一层"。
> 曾经只把"刚静音的"喂给门控 → **取消静音永远不重扫** → 窗口里那段被当作静音发过（没有 on），
> 而前瞻是单向的，于是音符扫过去是哑的（song 模式必现；PAT 模式因门控保守返回 true 而侥幸正常）。
| 拖动/拉伸提交（位置变化） | 释音 + 重扫 | `syncDragSnaps` + `muteNeedsRescanForClipMove` |
| 拖动换轨（进出静音轨） | 释音 + 重扫 | `muteNeedsRescanForClipMove` |
| 任意编辑提交（历史） | 可能重扫 | `scheduleWindowUnchanged`（窗口指纹） |

静音语义：**以后不再触发 + 此刻正在响的立即释音**（不是"等它响完"）。

## 7. 复杂度与已知上限

- `gatherRange` / 差分重扫都是 **O(片段数 × 音符数)**；
- 门控类判定是它的**子集**（只扫受影响片段），所以门控永远不比重扫贵；
**索引化方案（先量、再决定，暂未实施）**

现状：`gatherRange` / 差分重扫 / 窗口指纹都是 `O(片段数 × 音符数)` 的全扫描，
与"这一步真正要处理多少事件"无关（内层绝大多数 `nt.pattern != clip.pattern` 直接 continue）。

| 索引 | 做法 | 消掉的浪费 |
|---|---|---|
| 音符按样式分组 | `pattern → []note`（编辑后**懒重建**，O(N)） | 内层的样式过滤（通常 99%） |
| 片段按样式分组 | `pattern → []clip` | 外层只遍历该样式的片段 |
| 窗口活跃集 | 片段按 `start` 排序 + 维护"与 `[from,to)` 相交"的集合 | 远处片段完全不参与（注意：重扫会**回退**窗口，必须支持重建） |

- 效果：`O(片段 × 音符)` → `O(活跃片段 × 该样式音符)`，通常降 1~2 个数量级；
- **它不改善音频稳定性**（那些扫描在 **UI 线程**），改善的是"大工程的 UI 跟手度 / 重扫耗时"，
  以及降低"UI 卡顿饿死前瞻"的风险；
- **先量后做**：加一个"每帧调度耗时（平均/峰值 µs）"计数器，判定阈值：
  `<1ms` 不做；`1~4ms` 只做"按样式分组"；`>4ms` 或片段数 >1000 再上"窗口活跃集"；
- **风险**：索引必须在每次增删改后失效。做法是 **dirty 版本号 + 懒重建**，
  **不要**做增量维护（那是幽灵音符的温床）。
- `audio.stashInsert` 每条 **O(n)**（同键去重 + 有序插入）。重扫限窗后尖峰已显著降低；
  若将来仍见掉块，可改为"批量排序后一次归并（O(n+m)）"。

## 8. 回归测试

| 测试 | 保护的不变量 |
|---|---|
| `sched_stress.zig`：`sched stress (synth)` / `(VSTi)` | 随机拖动/静音 + 安全界抖动 + 同帧两次重扫，6000 块音频后 **`overrun == 0`** |
| `synth: note-off 按起点步精确匹配…` | 释音不误切同音高别的实例；同实例重触发不产生双声部 |
| `sched: 释音不误杀——切一个实例不得连带另一个同音高实例` | **端到端**：同一样式两条轨（起点 0 / 8），切掉起点 8 的实例后，起点 0 的声部必须仍在响（若退化成按音高 FIFO，此测试会失败——已验证） |
| `sequencer: 静音音符 on / off 都不发` | 静音内容不产生事件（避免误切其它轨同音高声部） |
| `app: 拖动静音轨里的片段不触发重扫` 等三条 | 不可闻/远期编辑不惊动音频线程（避免掉块） |

## 9. 变更史（教训）

| 曾经的做法 | 结果 |
|---|---|
| off 只走传输层 | 丢一条 = 永久挂音 |
| 静音内容"只跳过 on、off 照发" | off 按音高匹配 → 切掉**其它轨**同音高声部 |
| "off 永不作废" | 旧 off 在旧位置触发 → 新起的音只响音头 |
| 按 (音高, 乐器) FIFO 释音 | 同音高多实例时切错 |
| 各种"看着像挂了就补一条 off"的兜底 | 掩盖真 bug，且会砍合法长音 |
| **现在的做法** | on 带 `end_step` + 本地到点释音（结构性）+ 传输层 off（精确定时）+ 窗口指纹门控（避免无谓重扫） |
> 另记：**"补事件"式的修复对 VSTi 是危险的** —— 它没有声部模型，重复的 note-on 就是叠声部
> （实测：每切两次静音，整曲音量高一层）。凡是要"补"的地方，先想清楚目标音源是否幂等。
>
> 另记：**重扫门控的方向性**也曾出错 —— 只把"刚变成静音"的对象喂给门控，
> 导致"取消静音不重扫 → 音符扫过是哑的"。凡是"切换某状态"的操作，
> 门控与释音所需的集合**不一定相同**，别复用同一个 scope。

**收尾结论（2026-11，日志实证）**：静音切换路径上的"无谓重扫"已全部消灭 ——
`--sched-log` 下每次切换都能看到 `[mute] clips/track … rescan=false` 且
`[hist] … windowUnchanged=true`（即**完全没有调度工作**）。
若此时**仍有**轻微卡顿，那它已不在调度域，而属于实时性/UI 争用（见 §7 已知上限与 `docs/linux.md` 的 xrun 待办）。

## 10. 为什么有前瞻与重扫（架构审计，2026-11）

### 10.1 代码事实

| 环节 | 实现 | 位置 |
| --- | --- | --- |
| UI 每帧调度 | `scheduleRange([scheduled_upto, cur + 前瞻))` | `sequencer.zig` `scheduleRange` |
| 前瞻长度 | `steps_per_bar * 4`（4 小节） | `app.zig` 主循环 horizon |
| 传输通道 | SPSC 环形队列，容量 16384 | `synth.SchedQueue` |
| 音频侧缓冲 | 每 block 排空队列 → **按步排序的定长数组** `stash[2048]`，逐条**插入排序** | `audio.zig` `stashInsert` |
| 作废旧事件 | `gen`（传输跳变）/ `edit_gen`（编辑提交） | `audio.Params` |
| off 不靠通道 | `on` 自带 `end_step`，音频本地到点释音 | `audio.zig` |
| 重扫限窗 | `max_rescan_steps = 96` | `sequencer.zig` |
| 播放步 | **音频线程按采样自己算**（`start_step + elapsed/step_frames`），再写回 `last_step` 给 UI 画播放头 | `audio.zig` |

### 10.2 前瞻的真实作用（两条，别混为一谈）

1. **跨线程解耦（刚需）**：音频每 5–10 ms 要一个 block，UI 一帧可能几十到几百 ms（拖拽/插件界面/磁盘）。没有前瞻，UI 一卡就断音。这条需求只需要**几十 ms**。
2. **给重扫留补齐时间**：重扫会把水位线回退最多 96 步，需要若干帧才补回来。选 **4 小节（@120BPM ≈ 8 s）** 远超第 1 条需求 → 说明前瞻长度其实是被第 2 条撑大的。

### 10.3 重扫的根因：事件一旦推进队列就撤不回来

1. 队列是**单生产者单消费者环** → 推出去的事件无法删/改；
2. 所以编辑后只能“**粗粒度作废**”（`edit_gen += 1`，音频丢所有旧代事件但不打断在响的声部）；
3. 粗粒度作废意味着**未改动的音符也被作废** → 必须**整窗重发**（否则那部分静音）；
4. 整窗 = 上千条事件 → 音频侧 `stashInsert` 每条做一次插入排序（1000 条 × 平均挪 ~500 项 × 28 B ≈ 移动 28 MB）→ **毫秒级尖峰 → 掉块**。

> 逐层补丁（限窗 96 步、静音只扫一次、窗口指纹门控）都是在给第 3、4 步止血；
> **它们不是根因修复**，这也是为什么这个领域反复出问题。

### 10.4 为什么“把音符换成树”救不了

- 真正的约束与查找复杂度无关，而是：
  **(a)** 音频线程**不能分配、不能加锁**（实时安全）→ 只能读**只读快照**；
  **(b)** 已经派发出去的事件**不可撤回**。
- 增删发生在 UI 线程（几千音符的拷贝是**微秒级**），不是瓶颈。
- 正确方向：**只读快照 + 按步分桶索引**（数组的数组 / B+ 树都行——关键是“只读发布”）。

## 11. 演进计划：Pull 模型（方案 A）—— 作战计划

> 决策：**改走 A（音频线程拥有时间轴）**。B（可撕事件）作为**可选过渡**：成本小，
> 能先把“编辑提交 → 全窗重发”这条最贵的路径干掉，也是自动化的地基（自动化会高频改参，不能每次整窗重扫）。

### 11.1 目标形态

```
UI 线程：编辑 → 增量改“按步分桶索引” → 拍成**不可变快照** → atomic 指针/序号发布
音频线程：每 block 按 [block_start_step, block_end_step)
          从快照取音符 → 自己触发 on/off（end_step 本地释音已有）
```

- 结果：无事件队列（调度用途）、**无 lookahead、无 rescan、无 gen/edit_gen**；编辑下一个 block 就生效。
- 每 block 成本：只碰“这个 block 里开始的音符”（0–几十个），区间查询 O(k)。
- 注：**播放位置已经在音频线程算了**（`last_step` 由音频写回），所以 transport 搬家已经做了一半。

### 11.2 数据结构（草案）

```zig
const NoteEntry = struct { step: i32, len: i32, pitch: u8, inst: u8, vel: u8, pan: u8, nid: u32 };
const Bucket = struct { start: u32, len: u32 };   // 指向 entries 的子区间
const Snapshot = struct {
    buckets: []Bucket,      // 索引 = step（分页，step_base 支持长工程/循环）
    entries: []NoteEntry,   // 桶内按数组序（= 叠放层级，与 topmost 判据同源）
    lanes: []LaneRt,        // 自动化（参数曲线）共用同一份“按时间求值”骨架
    gen: u32,
};
```

- 快照发布：double-buffer + `atomic(active)`（或 atomic 指针）；旧快照**延迟 N 帧回收**（复用 retired 机制）。
- 桶数组**按需分页**（长工程不能整曲分配）。

| 阶段 | 内容 | 验收标准 |
| --- | --- | --- |
| **A0** | 量化基线：单次重扫事件数 / stash 峰值 / 调度耗时 µs / overrun 进每秒汇总 | 有数可对比 |

**A0 已完成（基线数字）**：

- GUI 侧：`--sched-log` 下每秒多一行 `[sched-cost] 1s: 前瞻 n=… avg=…us max=…us ev=…/max… | 重扫 n=… avg=…us max=…us ev=…/max…`
  （同时写进 `data/logs/sched.log`）——翻修前后直接对比这一行。
- 无头基准（`SAWDUST_BENCH=1` 跑 `sched_stress.zig` 里的 bench）：合成工程 **16 轨 × 4 小节、每步 4 音高（256 音符）**：

| 动作 | 推入事件数 |
| --- | --- |
| 前瞻推 1 小节 | **1,984** |
| 整窗推 4 小节 | **8,128** |
| 整段重扫（静音一条轨，即“全窗重发”） | **7,620** |
| Pull 模型每 block 需扫音符（≈4 步） | **256** |

→ 结论：**一次编辑提交要推 ~7.6k 条事件**（每条在音频侧做一次插入排序），而 Pull 模型每 block 只需见 ~256 个音符。
这是“为什么拖动/切静音会卡”的量级来源，也是 A 的收益上界。

**真机基线（Windows，用户自用工程 7,157 音符，`--sched-log` 日志，2026-11）**：

| 动作 | 频率 | 平均耗时 | 峰值 | 每次事件数 |
| --- | --- | --- | --- | --- |
| 前瞻推送 | 每帧 | **~200 µs** | ~0.8 ms | 7–19 条 |
| 静音限窗重扫（`muteTrackLive`，96 步） | 每切换 | **~180 µs** | 181 µs | ~58 条 |
| **编辑重扫（`rescanForEdit` 差分）** | 每次提交 | **8.4–10.2 ms** | 10.2 ms | ~60 条 |

**两个反直觉的结论（本审计最重要的发现）**：

1. **尖峰不在“事件多”**：`rescanForEdit` 只推 ~60 条事件却要 **9 ms**。成本在**差分算法**：
   `diffSide` 对每个唯一 `(音高, 乐器)` 对调 `crossingCount`，而后者**全量扫音符/片段** →
   O(P × N)（P ≈ 数百对 × N = 7,157）→ 数百万次访问 = 毫秒级。**与推事件无关**。
   （无头基准里 7,620 条事件/次是 `muteTrackLiveFull` 的**事件量**上界，真机上静音走的是限窗版，
   只推 ~58 条 —— 两者不矛盾，是两条路径。）
2. **前瞻每帧也在烧**：~200 µs/帧 × 45–60 fps ≈ **9–12 ms/s 纯扫描**（`gatherRange` 每调用
   扫全部音符，O(N)/帧）。

→ A 的收益因此是两件事：**去掉差分（9 ms × 每次提交）** + **去掉每帧的 O(N) 扫描**。

**实测缩放（同一工程不断加音符，`[rescan] EDIT … us=`）**：音符 7,157 → 编辑重扫 **~9 ms**；
音符 14,313 → **~19.5 ms**。**与音符数线性相关** —— 直接印证 `diffSide` 的 O(P × N)（P ≈ 常量）。
而**静音限窗重扫**同期只有 **182–306 µs**（它不做差分）——两者对比就是“差分到底多贵”的证据。

> **过渡机会（B-lite）**：不改变架构，把 `diffSide` 的“按对全量扫描”改成“一遍建表”
> （`(音高,乐器) → 跨游标计数/起点`），预计 8.7 ms → ~0.2 ms（~40×），约 30 行。
> 不影响 A，但能让 A1 的逐事件对拍跑得飞快，也能立即改善手感。

**A2 已完成（2026-11）**：快照发布 + 音频线程**影子对拍**（只统计，不发声）。

### 11.7 A3b 设计：每 block/每次换代**声部对账**（替掉 `release*` 特例）

**问题**：现在“编辑后谁该停止发声”靠一堆显式出口（`releaseJustMutedNotes` /
`releaseNotesNowForClips` / `releaseStaleAfterClipEdit`）。它们的共同风险是**按 (音高, 乐器) 近似释音**
（同音高多实例会误切），历史上反复出 bug。

**新规则（声明式）**：音频线程维护“**应该正在响**”的集合，与“实际在响”的集合对账。

- **何时对账**：只在 `snap_gen` 变化时（= 每次编辑提交后重建）；稳态不做任何对账（零成本）。
- **should 集合**：`snapshot` 中满足 `start <= cur_step < end` 的实例，按乐器聚成 `[128]` 音高位图
  （O(N) 一次，3.5k 实例 ≈ 十几 µs，且只在编辑后跑）。
- **对账动作**：
  1. 实际在响但 `should` 里没有 → **释放**；内置合成器按 `(音高, 乐器, start_step)` 精确匹配到自己的声部
     （`Voice.start_step` 已有），**不会误切同音高的另一个实例**；
  2. `should` 里有但没在响（编辑新增了“起点在游标之前”的音符）→ 补一条 on（`end_step` 用实例的），
     即“跨游标补发”；
  3. VSTi：**没有声部模型**，只能按音高发 note-off（同音高多实例仍不可区分——这条限制保留，
     与现有 `on_step` 匹配策略一致），文档与 UI 都不承诺更强语义。
- **可以删掉**：`releaseJustMutedNotes` / `releaseNotesNowForClips` / `releaseStaleAfterClipEdit`
  及其调用点（如果 A3b 验证后行为等价）。

**验收标准**：
1. `sched_stress` 全绿（改成“换代后 1 小节内不得有 `should` 之外的声部在响”）；
2. 真机：播放中切静音/删片段/拖片段/裁剪右端，**听不到残留音、也听不到被误切的音**；
3. 影子计数（现有 `[shadow]`）保持 0。
**A3 拆分（建议）**：`A3a` 换事件来源（音频改从快照取事件，**保留**现有释音路径与立即事件队列）→
`A3b` 用“每 block 声部对账”替掉 `release*` 一堆特例 → `A4` 删死代码（前瞻/水位线/`edit_gen`/门控）。
- 复杂度：`build` = O(片段 × 音符)（与现在“每帧一次 gatherRange”同量级，但只在**编辑时**做一次，
  而不是每秒 60 次）；`gather` = O(窗口内实例数)。
| **A1** | 只构建不启用：每帧构建桶索引，**与现有调度逐事件对拍**（离线断言） | 对拍 100% 一致 |
| **A2** | 音频线程“影子求值”：从快照求值但不发声，与队列结果对比 | 零不一致 |
| **A3** | 切主路：音频从快照发声；队列降级为**立即事件**（试听/all_off/CC/弯音） | `sched_stress` 全绿 + 手测 |
| **A4** | 拆旧：删 lookahead/水位线/`edit_gen`/`rescanForEdit`/门控/`max_rescan_steps`，改写本文 | 代码净减、无警告 |

### 11.4 风险清单

1. **快照回收 UAF** → 退役队列 + 断言（沿用 `retired_plugins` 那套“30 帧后回收”）；
2. **循环/跳转/SONG↔PAT 切换**的语义（现在的 `switchMode` 差分）→ 用“gen + start_step”在新模型里重新表达，并保位不释音；
3. **VSTi / CC 事件的逐采样定时** → 从快照生成参数事件时保持 sample-accurate；
4. **长工程内存** → 桶数组分页，不整曲分配；
5. **音频线程零分配** → block 内只用栈/预分配缓冲。

### 11.6 A 之后能解决什么 / 不能解决什么

| 现象 | A 之后 | 原因 |
| --- | --- | --- |
| 4 小节窗口内改静音/拖动导致的**卡顿、短暂消音** | ✅ 消失 | 没有重扫，就没有整窗重发 → 没有 `stashInsert` 尖峰 |
| 挂音（off 丢失） | ✅ **结构性消失**（内置合成器） | 每 block 把“在响的声部”与“按快照应该响的”**对账**，不再依赖事件通道 |
| `release*` 那一堆特例入口 | ✅ 可删 | 释音从“事件驱动 + 一堆门控”变成“**每 block 一次对账**” |
| “播放中放到游标前方的音符不响” | ✅ 消失 | 快照即时生效，不存在“已扫过的窗口” |
| 静音切换的 UI 尖峰（非调度域） | ❌ **不变** | 属于实时性/UI 争用（`docs/resources.md` + 电源节流），与 A 无关 |
| VSTi 的“同音高误切” | ⚠️ **仍需旧机制** | 插件没有声部模型，无法逐实例对账 → 保留 `pitch + on_step` 匹配 |
| **BPM 跟随自动化曲线** | ⚠️ **解锁但需独立工作包** | 见下 |

**为什么 A 能让 BPM 自动化成立**：现在事件在推入时就把 step 换算成了固定采样时间，
中途改 BPM = 已排程事件的实际时间全错 → 必须重排窗口。Pull 模型下**时间是每个 block 当场算的**
（`step_frames` 按当时 tempo 积分），改 tempo 只是“下个 block 用新值”，**不需要任何重排**。

但 BPM 自动化本身仍是独立工作包（A 不送）：

1. **tempo map**（分段阶跃 / 曲线求值 + 单调积分，避免累积误差）；
2. 跟随 BPM 的子系统：卡拍延迟/混响时间、音频片段播放速度（是否随 BPM 拉伸是产品决策）、VSTi 的 `ProcessContext.tempo`、
   波形与时间轴显示（步↔像素）；
3. 监听平滑（延迟时间变→尾音拉伸/音高变化），必要时限制变化速率；
4. 建议分两步：先做**整小节**的阶跃 tempo（记进 MIDI 导出为 set-tempo 元事件），再做连续曲线。

### 11.8 现行模型（pull）：快照驱动 + 换代对账

**数据流**

```
UI 线程：编辑 → commitHistory → snap_dirty
        每帧 pollSnapshotRebuild()：脏则 build 快照 → atomic 发布(snapshot_ptr) + snap_gen++
                                    旧快照进退休队列，30 帧后释放
音频线程：每 block
          · snap_gen 变化 → 丢弃 stash 待触发事件 + snap_step = 本块起点 + **换代对账**
          · 从快照取 [snap_step, s1) 的事件 → stashInsert → 原有触发流水线
          · s1 用 **ceil**（`k*step_frames < D` ⇔ `k < ceil(D/step)`，floor 会每块错一位）
```

**不变量（现行）**

1. **快照是唯一权威**：调度不再有“已推未触发的事件”这层状态——stash 只是**本块工作集**；
2. **换代即生效**：`snap_gen` 变 → 清 stash + 从当前块重发 → 编辑最迟**一个 block** 生效，
   没有水位线、没有前瞻、没有重扫；
3. **对账保证声部一致**（§11.7）：换代时把“在响的声部”校正到快照的“应该响的”，
   内置合成器按 `(音高, on_step)` **精确**释放（不误切同音高实例）；VSTi 只能按音高（已知限制）；
4. **off 仍然双保险**：`on` 自带 `end_step`，音频本地到点释音（与模型无关，保留）；
5. **快照不可立即释放**：音频可能正在读旧快照 → 退休队列 30 帧（实测 block ≈10 ms）。

**诊断（现行）**

| 指标 | 含义 |
| --- | --- |
| `[shadow] 1s: 路径=快照 块=… 不一致 on/off=…` | stash（本块工作集）与快照的逐块比对；**不一致必须为 0** |

### 11.9 鼓组（kind == 1）纳入对账

**语义定案（用户拍板）**：**pad 就是音高**（`kit_layer_pitch == ev.pitch` 触发该层），
与普通乐器一致 —— 同 pad 重叠触发 **两个声部都该响**（实例级，不是 mono-per-pad）。

已落地：

- **对点释音**：本地 `end_step` 释音**本来就覆盖**鼓组合成器层池（`kitPool(engine, i)`，与普通乐器同款）✓；
- **采样器层**：`SamplerVoice` 新增 `start_step`（实例标识），`kitSamplerNoteOn` 带上 `on_step`；
- **换代对账**（`reconcileVoices` 的 `1b` 分支）：
  - 合成器层 → 按 `(pad, layer, start_step)` **精确**释放；
  - 采样器层 → 按 `(pad, start_step)` 把 `active = false`（精确到实例）；
  - VSTi 层 → 按 pad 发 note-off（**无声部模型，已知限制**，与普通 VSTi 同）；
- 单测：`audio: A3b 鼓组对账——同 pad 两个实例只停被删的那个`。

**已删（2026-11，用户真机验证鼓组工程后）**：`releaseJustMutedNotes` / `releaseNotesNowForClips` /
`releaseStaleAfterClipEdit` / `releaseJudgeStep` / `clipAudible` 及其调用点。
**释音现在只剩两条声明式路径**：

1. **换代对账**（`reconcileVoices`）：内置合成器 / 鼓组（合成器层·采样器层·VSTi 层）/ 普通 VSTi；
2. **本地到点**（`end_step`）：内置合成器 + 鼓组合成器层 + VSTi 位图。

不再有“某处编辑要记得调用某个 release 函数”的可能——这是 A 计划的最终目标。
